Testing PR-derived
Python guidance

A comparison of 20 Codex sessions on two Robo Radian pull requests

We wanted to know whether adding six PR-derived Python rules to the repository’s usual guidance improved the submitted patches. We tested five sessions per group on each of two Mathspace tasks.

PR goals and review feedback

Robo Radian, Mathspace’s coding bot, authored both PRs. A maintainer confirmed the Codex review findings and updated both patches.

PR #20388

Head-teacher class lookup

Original goal

Use the teacher’s stored school ID to list classes without fetching the school first.

Review feedback

  • The direct lookup lost the school cache. isUnsyncedClass could fetch it once per class.
  • Adding a school join to the shared query broke CSV export, which loads only class titles.

Merged approach

Load the school only when GraphQL fields need it.

PR #20462

Chapter-link sync

Original goal

Batch repeated lookups for links between a subtopic and its chapters during imports and admin saves.

Review feedback

  • Two concurrent syncs could both try to insert the same link and hit a uniqueness error.
  • Retrying safely with one savepoint per link still made database work grow with the number of links.

Merged approach

Use one savepoint for the batch and retry safely if a competing sync inserts a link.

On PR #20388 the original change removed the round trip just to construct the head-teacher class query. The first review found that the old reverse lookup also cached the school on the returned classes. An unconditional school join fixed the GraphQL query growth, then a second review found that it broke the CSV path using .only("title"). The final patch loads school in the GraphQL resolver when school or isUnsyncedClass is requested and leaves the shared queryset compatible with partial field selection. School cache review · CSV review and maintainer response.

On PR #20462 the first review found that a batch of existing links can go stale before insertion. The first fix handled a competing insert with a nested transaction per link. The next review pointed out that each nested transaction added a savepoint and release inside the admin transaction. The merged fix uses one transaction for the missing-link batch and recovers after a uniqueness conflict, including a conflict after earlier links were inserted. Treatment rules · 1–3

  1. Preserve the whole contract. Trace the changed helper through its real callers. Preserve scope, return shape, ordering, duplicate and empty cases, and error behaviour unless the task explicitly changes them. A local improvement must not weaken nested authorization or expose additional data. Check assumptions against the producer and consumers.

  2. Keep data access bounded and composable. On collection paths, avoid repeated queries and unnecessary eager materialization. Keep ORM ID selections as database queries when they compose into another query, unless a cross-database boundary or another concrete reason requires materialization. Consider which dimension grows; do not claim that all queries are constant because one component is.

  3. Test the behavioural boundary and scaling. Use realistic fixtures to check results, not just that a helper was called. For an optimization, compare empty, single and multiple inputs where meaningful, include overlapping and unrelated data, and measure the relevant query count or SQL. A regression test should distinguish the original problem from the fix where feasible. Do not require arbitrary exact query counts where they are not part of the intended contract.

The numbered rules are quoted verbatim from the treatment override.

Treatment rules · 4–6

  1. Make data and side-effect ownership clear. Keep shared helpers small and focused; use framework facilities for the work they own. Preserve lazy/eager return contracts. For changes involving writes, publish jobs, events or emails after successful commit where required, and test the actual transaction boundary. Do not add speculative layers or swallow errors.

  2. Use types as truthful contracts. Preserve supported input and return types and framework signatures. Derive types from actual producers; validate untrusted input at runtime instead of casting it to make type errors disappear. Prefer a narrow justified suppression to changing behaviour merely to satisfy a checker.

  3. State evidence and limits. Run relevant checks when possible. Report the exact behaviour and measurements verified, untested cases, and any assumptions. Fixture-level query counts do not prove production latency or query plans.

How we graded the patches

Validate the tests

Before the runs, reproduce each bug on its pre-fix commit and confirm that the merged fix passes. Check that existing behavior passes on both commits.

Grade the saved patch

Apply the patch in a separate checkout. Run the tests kept out of the agent workspaces with python -m pytest -q on disposable PostgreSQL 17.

Count a pass

A patch passed if every expected test case ran and passed, including checks for behavior that should stay the same.

PR #20388 · Class lookup

School query counts in the model and GraphQL, plus teacher CSV export.

PR #20462 · Chapter links

Query and savepoint counts across batch sizes, plus recovery from concurrent inserts.

The coordinator selected regression tests from the merged fixes and added existing-behavior checks. Each task showed a regression on the pinned base. All selected cases passed on the merged fix, and the existing-behavior checks passed on both. The selected tests gave 28 expected pytest cases for #20388 and 7 for #20462.

The grader applied each saved patch to a clean copy of its starting commit, including the copies captured at the time limit. It then overlaid and hash-checked the grading files. Pytest ran the selected tests and produced JUnit results. A pass required a zero exit code, the exact expected case IDs, and a pass for every case. The archived grader also ran lint, formatting, and type checks as secondary measures.

What the treatment patches did

Head-teacher class lookup

Two treatment patches fixed the basic lookup and tested school { title } through viewer. The hidden node(id:) query for isUnsyncedClass still went from 2 school reads for one class to 6 for five.

The three passing treatment patches also updated the GraphQL resolver.

Chapter-link sync

Two treatment patches and one control patch batched the writes and passed the competing-insert checks. All three failed the same requirement. The grader expected zero savepoint commands for an empty list, and each patch created and released a savepoint.

The two head-teacher misses used school_id to remove the model-level lookup and both added useful scope and GraphQL coverage. Their tests covered the school title through viewer. The frozen grader also checked the node entry point and a field that reads school-related state. That combination still caused query growth.

After the runs, we regraded the same chapter-link patches allowing one savepoint pair for an empty list. The pre-fix code still failed and the merged fix still passed. Chapter-link scores rose to 5/5 for control and 5/5 for treatment. Across both tasks, the alternate scores were 10/10 and 8/10. The primary comparison uses the test criteria defined before the runs.

Conclusion

Adding prompt instructions does not guarantee better performance.

Control passed 9 of 10 runs. Treatment passed 6 of 10 under the criteria set before the runs.

The study tested all six rules together on two selected performance PRs.

The study estimates the performance of the six-rule bundle on these tasks at the tested model setting. Five runs per group on each PR show how results varied within the two tasks.

The separate empty-list check narrowed the observed gap. Control still had more passing patches overall. The primary conclusion uses the grading criteria set before the sessions.

Reproducing the grading

Replaying the saved patches reproduced the pass status and individual test outcomes for all 20 runs.

  • Start from the pinned pre-fix commits in the Mathspace repository.
  • Apply each saved patch in a separate copy of its starting snapshot.
  • Run the held-out pytest suite on disposable PostgreSQL 17.

Patch replay requires access to the Mathspace repository and the internal reproduction packet.

The replay script verified patch and grader hashes, then compared the exact pytest case outcomes with the recorded results. All 20 patch outcomes and sets of individual test results matched.
